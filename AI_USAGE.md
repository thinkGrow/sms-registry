# AI Usage

I built this whole project with Claude Code running as a VS Code extension, working directly inside the same editor and terminal I was coding in, not a separate chat window disconnected from the project. That mattered in practice: Claude could read the actual files in the repo, run commands in my own terminal (start the dev server, run migrations, curl live endpoints, query the database), and see real output, rather than generating code from a description in isolation and hoping it matched what was actually there.

## How I worked with it

For plumbing and scaffolding, I described a feature in plain language ("add hard delete for students," "add search and filter to the students list") and let Claude propose the structure, then reviewed the result and asked for changes. For the actual business logic, the four enrolment statuses, fee installment billing, deferral and withdrawal timing, I gave detailed, structured rules up front rather than a vague prompt, because getting these wrong doesn't fail loudly, it just silently computes the wrong balance. As an example, "a deferral takes effect on the 1st of January the following year, not the day it's set, then freezes the fee schedule for one assumed year before resuming" was handed over as an exact rule to implement, not a general idea for Claude to interpret on its own. Even with a precise spec, some of these rules changed once I saw them behave incorrectly in practice, and one deferral-timing decision got reversed entirely partway through the build after I thought it through further and asked Claude to revert to the earlier model.

I stayed the decision-maker on anything ambiguous or scope-related. Claude implemented, flagged edge cases and trade-offs I hadn't considered, and pushed back directly when I was over-scoping something the timeframe couldn't support (stacking module registration and prerequisites on top of an already-agreed fee-override decision) or when an instruction would have broken something already working correctly (letting deferred students keep submitting coursework just because a deadline hadn't passed yet).

## Testing: manual and automated

I tested this two ways throughout, not just one.

Manually, in the actual browser: switching between the staff and student roles through the app's own toggle, clicking through every form and dialog, uploading real files, watching how the UI actually rendered. This caught real bugs that command-line testing never would have: a Select dropdown showing a raw database ID instead of a programme name, an edit dialog reopening with stale values because React Hook Form's `defaultValues` only compute once per mount, a layout width bug that only showed up as a shrink-wrapped header in DevTools. Claude doesn't have browser automation, so anything visual or interactive ultimately needed my own eyes on it.

With code: after nearly every backend change, Claude ran curl requests directly against the live API routes and checked the actual database and rendered HTML, rather than reading the code and asserting it should work. It verified both the happy path and the edge cases (a rejected duplicate email, a student blocked from grading someone, a payment correctly capped once a fee's fully paid), and more than once deliberately reproduced a bug live before fixing it, for example watching a student's installment count drop the instant they were marked deferred, confirming a flat "subtract a year" model was retroactively erasing an installment they'd already started, before building the actual fix. Later in the project I also added a small Vitest unit test suite (`npm test`) specifically for the trickiest, previously-buggy pure logic, the deferral/withdrawal billing math and grade classification thresholds, so that logic now has an automated regression check going forward instead of relying only on having been manually verified once.

## What stayed mine

Every product and scope decision, what each of the four modules actually needed to do, which edge cases mattered, what to explicitly leave out and document as a limitation rather than build, was mine. I wrote the early Zod validation schemas myself with Claude working from a spec I gave it, specifically to keep that logic in my own hands while the pattern was still being established, and only let Claude write schemas directly once that pattern was solid. Any destructive or interactive database operation, a migration needing a manual backfill decision, a full reset, I ran myself in my own terminal rather than have Claude run it; Prisma itself refused to run some of these non-interactively, correctly treating them as something a human should confirm first.
