# AI Usage Log

I built this project with Claude Code as a collaborative pair programmer. Each entry documents a step: what I did, and how I used AI versus what I reviewed or decided myself.

### Setup
- I scaffolded the app with `create-next-app` (TypeScript, App Router, Tailwind, ESLint, `src/` dir, `@/*` import alias), using commands Claude suggested and running them myself in the terminal.
- The scaffold generated `AGENTS.md`/`CLAUDE.md` files flagging that Next.js 16 has breaking changes versus what's in Claude's training data. I agreed with Claude that it should check `node_modules/next/dist/docs/` before writing framework-specific code, instead of assuming older App Router conventions still apply.
- I asked Claude to keep commit messages structured (Conventional Commits: `feat`, `fix`, `chore`, `docs`, `test`, `ci`) for the rest of the project, and to log that instruction here.

### Design system
- I ran `shadcn@latest init` interactively in my own terminal, landing on the `base-sera` style with the `taupe` base color.
- Before adding feature components, I asked Claude to confirm a centralized color system and reusable components already existed. Claude verified shadcn's CSS variable token system and the existing `cva` based `Button` component, then extended `globals.css` with app specific semantic tokens (`success`, `warning`, `info`) for status flags like enrolment status, overdue fees, late submissions, and grade classification. These are defined once, for light and dark, rather than as one off colors per page.

### Database setup
- I added `docker-compose.yml` for local PostgreSQL, choosing that over a hosted database so anyone cloning the repo can run it with zero account signup, and the same image can later back a CI service container.
- I ran `npx prisma init`, which generated a placeholder `DATABASE_URL` pointing at Prisma's own hosted `prisma+postgres://` dev service instead of a plain Postgres connection string. Claude caught this and replaced it with the actual Docker Postgres connection string, and added the missing `dotenv` dependency that `prisma.config.ts` requires.
- I filled in the README's "Getting Started" and "Environment Variables" sections with the real setup steps once they existed, replacing the earlier placeholders.

### Schema design: Student and Programme
- Claude and I discussed the field by field reasoning for `Student` (a separate `id` versus a human facing `studentId`, `@db.Date` for date of birth, an enum for status, audit timestamps) and `Programme` (`Decimal` for money instead of `Float`) before writing the schema.
- I raised that students may get discounts through multiple programmes, financial aid, or scholarships. Claude recommended against building full subsystems for these, since they're out of spec scope and would crowd out the four graded modules given the time I have left. Instead we agreed on a single optional `feeOverride` field on Student, with the one programme per student simplification and its trade offs documented explicitly in the README rather than silently ignored. I decided the fuller logic can be layered in later once the core project is complete.
- We discussed why `academicYear` has to stay a plain editable field rather than being derived from enrolment date, because a retake can put a student in the same academic year twice. We also agreed enrolment `status` should gate assessment submission eligibility.
- I settled on Zod as the project wide validation convention, reused between forms and API routes, after asking Claude why client side validation alone isn't sufficient (a public API route can be hit directly, bypassing the form).
- I asked Claude to explain how to visualize the database design. We went with a hand maintained Mermaid ER diagram in the README instead of an auto generating tool like prisma-erd-generator, since it needs no extra dependency and GitHub renders it natively.

### Schema design: Payment and fee due dates
- I asked to discuss the Payment model entirely from scratch rather than refining an earlier draft. Claude restated the four open questions plainly: whether payments are installment style, where the reference number comes from, what defines an overdue balance, and whether a recorded payment can be edited.
- I confirmed payments are installment style, multiple rows accumulate toward a student's fee.
- I asked whether the reference number could be auto-generated instead of staff-entered. Claude agreed this was the better call since the app doesn't integrate with a real payment gateway or bank, so there's no external reference to capture, and generating it the same way as the Student ID avoids relying on staff data entry for uniqueness.
- I ruled out a "days since enrolment" definition of overdue, since a fee amount doesn't change based on what day someone signed up, and rejected "balance greater than zero" as too blunt since it would flag a student overdue on day one before any real deadline passed. I settled on a per-programme due date instead.
- I confirmed payments should be ordinary CRUD rather than a full accounting ledger with reversal entries, and asked Claude to document that as a deliberate scope exclusion in the README rather than leaving it unstated.

### Schema design: Assessment and Submission
- I asked Claude to explain the difference between a programme and a module, since the spec lists both but only defines Programme as its own entity. Claude clarified that Programme is the whole degree while module is one subject taught within it, and proposed keeping module as a plain text field on Assessment while adding a programmeId relation purely for submission eligibility.
- I pushed back that a student in Computer Science might not be registered for every module under it, exposing a real gap in programme-level eligibility scoping. I then raised that modules can also have prerequisites between each other.
- Claude named this directly: each concern I raised was individually valid, but stacking module registration and prerequisites on top of the earlier fee discounting discussion would turn one module of four into the entire remaining project. I agreed to keep programme-level scoping on Assessment and document the module-registration and prerequisite gap as a known limitation instead of building it.
- We finalized Assessment (title, module as plain text, programmeId, a full datetime deadline rather than a date, since lateness depends on an exact cutoff) and Submission (fileUrl, fileName, an enum fileType restricted to PDF or DOCX, a unique constraint on studentId and assessmentId so resubmission overwrites the existing row instead of keeping history, and isLate computed from updatedAt versus the assessment deadline rather than stored).

### Schema design: Grade
- I confirmed grades should allow half points, so I used Decimal instead of Int for score, matching the same reasoning as money fields, since the classification thresholds need exact comparisons rather than floating point.
- Claude pointed out the spec never names what a score under 40 is called, and I agreed treating it as an implicit Fail, computed at read time rather than stored, was the obvious resolution.
- Claude flagged a real ambiguity in the spec's wording, "publish or withhold results per student" could mean one switch for a student's entire marksheet, or a separate publish flag per individual grade. I confirmed per grade makes more sense, since staff would realistically publish results assessment by assessment as grading finishes rather than all at once.

### Seed script and a Prisma version surprise
- Claude wrote prisma/seed.ts covering every edge case we designed for in one pass: overdue balances, a fee override, all four enrolment statuses, a late submission, and a withheld grade, rather than generic placeholder rows.
- Rather than assume the old package.json convention for configuring the seed command, Claude checked the installed Prisma version's actual type definitions and found the seed command now lives under migrations.seed in prisma.config.ts instead.
- The seed script failed twice in a row on things Claude's training data wouldn't have known about in this Prisma version: the generated client has no index file, so it has to be imported from client.ts directly, and this generator requires an explicit Postgres driver adapter (@prisma/adapter-pg) rather than connecting automatically the way older Prisma versions did. Claude read the generated client's own source to confirm this instead of guessing, then set up a shared prisma client singleton at src/lib/prisma.ts using the adapter, which the seed script now reuses instead of instantiating its own client.

### Student Enrolment module
- I confirmed no hard delete for students, WITHDRAWN status covers a student leaving instead, so Claude only built create, read, and update endpoints.
- Before writing the dynamic route for a single student, Claude checked Next.js's own bundled documentation rather than assume the params shape from training data, since the scaffold's AGENTS.md file had already warned this Next.js version has breaking changes. It confirmed params is a Promise that needs awaiting, which is what got built.
- Claude wrote the Zod validation schemas, the sequential student id generator, and both API route files, then started the dev server itself and ran curl requests against every endpoint (list, search, status filter, create, single fetch, update, duplicate email, invalid email) to verify each one before telling me it was done, rather than just asserting the code should work. It found the newly created test student got an SMS-2026 id while the seed data uses SMS-2025, since the generator uses the real current year rather than the spec's illustrative example year, and explained that wasn't a bug. It then re-ran the seed script to remove the test record it had created during verification, restoring the clean seeded dataset.
- I said going forward I want to write Zod schemas myself, with Claude giving instructions instead of writing that file directly.

### Student Enrolment UI
- Claude added the select and dialog shadcn components. The form component didn't install, view form on the registry returned an empty entry, which Claude attributed to this project using Base UI instead of Radix as its primitive library, since the shadcn form wrapper may not be ported to Base UI yet. Rather than fight that, it built the form directly with React Hook Form against the existing Input, Label, and Select components instead of the shadcn form wrapper.
- Claude built the students page, a filter bar, a table, and a create and edit form dialog, then started the dev server and curled the page rather than assuming it worked. That surfaced two real bugs: Prisma's Decimal type can't cross the Server to Client Component boundary as is, so Claude added a serialize.ts helper converting Decimal fields to plain numbers before passing data to client components, and the Dialog trigger used a Radix style asChild prop that doesn't exist on this Base UI based component, which Claude caught by reading the actual dialog.tsx source rather than assuming, and fixed using this component's own render prop pattern instead.
- Claude also caught and rewrote its own first draft of the Select field wiring, which manually dispatched a fake onChange event into react-hook-form's register function. That was fragile, so it replaced it with react-hook-form's Controller component, the standard way to connect a non native form control to react-hook-form.
- After both fixes, Claude re-verified server side rendering was clean before handing it back for me to click through in an actual browser myself, since it doesn't have browser automation tools to test the interactive dialog and form submission directly.
- I found a real bug through actual browser use that curl testing couldn't have caught: the programme filter dropdown displayed the raw database id instead of the programme name. Claude traced this to Base UI's Select.Value component, which needs an explicit children render function mapping the selected value to a label, unlike Radix which does this automatically by matching against the rendered SelectItem. It fixed all four Select instances across the filter bar and the form dialog, then verified the fix by checking the actual rendered HTML output for the programme name rather than just asserting the code change should work.
- I reported date of birth wasn't saving. Claude first tested the API directly with curl and confirmed it persists date changes correctly, narrowing the bug to the form itself. It then identified a real React Hook Form gotcha: useForm's defaultValues are only computed once, when a component first mounts, and since the same edit dialog instance for a table row isn't destroyed and recreated just because its student prop's data changed after a save, reopening Edit on that row was showing the stale values captured at first mount rather than the freshly saved record. It also noted the table doesn't display date of birth anywhere, so reopening Edit was the only way to check it, which is exactly the scenario that triggers this bug, supporting that diagnosis. The fix keys each row's dialog on the student's updatedAt timestamp, forcing a fresh mount whenever the record actually changes.
- I asked where to see a student's full info, since the table only shows a summary. Claude added a read-only student detail page at /students/[id], linked from the table, reusing the same edit dialog from there too. It verified the Button component's render prop (used to compose it with a Next.js Link) actually exists on this Base UI component before using it, by checking the library's own type definitions rather than assuming, and caught a repeat of the earlier Decimal serialization bug on this new page (the student's nested programme relation wasn't re-serialized before being passed to the client-side form dialog), fixing it before handing it back.
- I reported date of birth showed correctly on the detail page but not in the edit form itself. Claude traced this by reading Base UI's actual Input implementation (it turned out to be a wrapper around their Field.Control component, with its own internal ref and value handling separate from a plain native input), but couldn't fully verify the exact cause without live browser testing. Rather than keep guessing, it converted the date field to a fully controlled input via react-hook-form's Controller, the same pattern already used successfully for the two Select fields, removing the dependency on uncontrolled defaultValue behavior entirely regardless of the precise internal cause.
